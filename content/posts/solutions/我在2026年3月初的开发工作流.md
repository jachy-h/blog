> 以下记录的是 **2026 年 3 月初**使用的工具组合与任务分工。工具套餐、模型可用性和免费额度会变化，本文侧重任务分配思路，不作为当前套餐推荐。

## 问题：不同任务是否应该使用同一套工具？

当时我同时使用 GitHub Copilot、Qwen Code 和 OpenCode。面对有限的付费额度，我选择按任务复杂度分配工具，而不是让所有任务都走同一条路径。

这是一份个人实践记录，还没有通过固定任务集做对照测试，因此不能据此判断哪个工具的整体能力更强。

## 我的任务分配

| 场景 | 当时的处理方式 | 预期产物 |
| --- | --- | --- |
| 复杂功能与架构设计 | 使用 Copilot 中的 Opus 先完成计划 | 设计文档与待办文件 |
| 简单需求开发 | 使用 Qwen Code 或 OpenCode | 可以检查的代码改动 |
| 复杂需求开发 | 使用 Sonnet | 围绕复杂需求的实现 |
| 故障修复 | 先尝试 Qwen Code 或 OpenCode，无法解决再交给 Sonnet | 修复方案与代码 |

这里的工具选择有明确时间背景：当时 Copilot 是我的主要付费工具，Qwen Code 和 OpenCode 则补充日常开发。套餐与额度变化后，具体组合也需要重新判断。

## 先把设计变成文件

对于复杂任务，我先让工具产出设计文档和待办，再进入实现。这样任务交接有了明确的文件载体，也便于回看最初的目标。

设计与实现分开，并不自动保证结果正确。计划仍需要人工判断，代码也需要检查和验证。文档的价值在于把讨论留下来，而不是替代验收。

## 多个工具并行时，隔离工作区

我也用 `git worktree` 为不同任务建立工作区与分支。相关命令保留在[Agent 工具笔记]({{< ref "posts/solutions/My Agent Team.md" >}})中。

工作区隔离只能减少文件互相覆盖；接口约定、合并冲突与最终验收，仍需要明确处理。

## 这份工作流还缺少什么证据

目前记录了任务分工方式，还没有记录同一任务在不同工具下的耗时、返工次数和验证结果。后续评估时，我希望围绕这些问题补充实际案例：

- 一个任务从设计到验收经历了几次交接？
- 较低成本工具产出的代码，需要多少人工修正？
- 更换工具是因为任务难度，还是因为上下文没有交代清楚？

现阶段可分享的是一种分配思路：**先辨认任务，再选择工具，把设计产物与代码改动保留下来。**是否节省成本、是否提高交付质量，还需要具体任务的数据支持。
