> 记录的是 2026 年 3 月初的工具组合。套餐、模型和免费额度都会变，这里只谈任务分配，不作为当前推荐。

## 不同任务该用同一套工具吗

当时我同时用 GitHub Copilot、Qwen Code 和 OpenCode。付费额度有限，就按任务复杂度分配，没有让所有任务走同一条路。

这是一次个人实践，没有用固定任务集做过对照，不能据此判断哪个工具更强。

## 当时的分工

| 场景 | 当时的处理方式 | 预期产物 |
| --- | --- | --- |
| 复杂功能与架构设计 | 使用 Copilot 中的 Opus 先完成计划 | 设计文档与待办文件 |
| 简单需求开发 | 使用 Qwen Code 或 OpenCode | 可以检查的代码改动 |
| 复杂需求开发 | 使用 Sonnet | 围绕复杂需求的实现 |
| 故障修复 | 先尝试 Qwen Code 或 OpenCode，无法解决再交给 Sonnet | 修复方案与代码 |

Copilot 是当时的主要付费工具，Qwen Code 和 OpenCode 补日常开发。套餐和额度一变，这个组合就得重新判断。

## 先让设计落成文件

复杂任务先让工具产出设计文档和待办，再进入实现。这样交接有文件可看，也能回头核对最初的目标。

设计和实现分开，不保证结果一定对。计划要人判断，代码要检查和验证。文档的作用是留下讨论，不替代验收。

## 并行时隔离工作区

我也用 `git worktree` 给不同任务开工作区和分支，命令记在[Agent 工具笔记]({{< ref "posts/solutions/My Agent Team.md" >}})里。

工作区隔离只能减少文件互相覆盖。接口约定、合并冲突和最终验收，还是得单独处理。

## 还缺哪些数据

现在只记了怎么分工，没记同一任务在不同工具下的耗时、返工次数和验证结果。后面想补几个实际案例：

- 一个任务从设计到验收经历了几次交接？
- 低成本工具产出的代码，需要多少人工修正？
- 换工具是因为任务难度，还是因为上下文没交代清楚？

目前能说的只有分配思路：先看任务，再选工具，把设计产物和代码改动留下来。至于是否更省成本、交付质量是否更好，得看具体任务的数据。
