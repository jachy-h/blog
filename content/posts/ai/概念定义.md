阅读 API 示例时，很容易把 `role` 理解成显示在聊天窗口里的身份标签。更有用的理解是：它标记消息来源，参与模型对指令与上下文的处理。

不同 API 的数据结构存在差异，不能将一张角色表直接当作所有端点的请求格式。

## 先理解消息来源

| 名称 | 阅读代码时如何理解 |
| --- | --- |
| `developer` | 应用开发者提供的行为规则；官方文档明确其指令优先于用户消息。 |
| `user` | 终端用户提交的请求与输入。 |
| `assistant` | 模型生成的消息，可作为后续对话上下文。 |
| `system` | 在部分接口或兼容示例中出现的指导消息角色；是否使用应核对目标端点和模型文档。 |

角色名称不表示事实可信度：`assistant` 的回答可能出错，工具结果也需要结合调用来源理解。应用应根据所用 API 的规范组织消息，而不是把所有内容都拼成用户输入。

参考：[OpenAI 文本生成指南](https://developers.openai.com/api/docs/guides/text)。

## 工具结果不总是 role 为 tool 的消息

Chat Completions 与 Responses 的工具调用结构不同：

| 观察对象 | Chat Completions | Responses |
| --- | --- | --- |
| 对话数据 | `messages` | `input` / `output` 中的类型化条目 |
| 函数调用 | assistant 消息中的工具调用 | `function_call` 条目 |
| 函数结果 | 对应调用的 `tool` 消息 | `function_call_output` 条目，通过 `call_id` 关联 |

因此，看到 Responses 示例中的 `function_call_output`，不要把它改写成 `role: "tool"`。移植示例时需要同时核对条目类型和调用关联字段。

旧示例还可能使用 `function` 角色。处理这类代码时，应先确认接口年代和目标 API，再按照对应迁移说明调整。

参考：[迁移到 Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses)。

## 我的阅读顺序

遇到陌生示例时，先看调用的是哪个端点，再看消息或条目类型，最后看工具调用与结果如何配对。这个顺序有助于区分“对话角色”和“执行过程”，避免只替换字段名却保留错误结构。
